# TDCloud 通用商户收款能力需求

## 背景与归属

外部商户系统（首个使用方为 ZBoard）拥有自己的业务订单、交付和订阅状态。TDCloud 作为支付渠道，需要提供不依赖 TDCloud 商品或买家账号的通用收款订单。资金沿用 TDCloud 平台代收，并按 TDCloud 自己的账务规则记入商户结算钱包。这是 TDCloud 面向任意商户系统的能力需求，不要求 TDCloud 识别或更新 ZBoard 订单。

TDCloud 项目应先评审其支付、订单、钱包、OAuth、风控和对账边界，再决定内部模型、路由、权限名、支付提供商及首期币种。本文件仅定义外部调用方必须获得的行为，不指定表结构或实现方式。

## 外部能力

1. **创建收款单**：商户服务端凭据提交外部订单引用、十进制金额字符串 `amount`、币种、幂等键及可选描述；内部支付方式交给 TDCloud 收银台，不提交 `payment_no`；返回 TDCloud 收款单号、可跳转的 HTTPS 收银台地址、过期时间及当前状态。金额由商户提交，不要求预先创建 TDCloud 商品。
2. **幂等建单**：同一商户、同一幂等键和相同参数重复请求，返回同一收款单；参数变化明确拒绝。网络超时后的重试不能生成第二笔可支付收款单。不同商户的幂等空间隔离。
3. **服务端查单**：商户凭据只能查询自己的收款单。结果包含不可变的外部引用、十进制金额 `amount`、币种、渠道标识，以及 `pending`、`paid`、`failed` 等可映射状态。已支付结果提供稳定、唯一的支付事件号、渠道交易号和支付时间，供外部系统幂等记账。
4. **可信结算**：TDCloud 自行验证支付提供商结果，完成商户钱包入账和账务记录；只有收款与商户结算均确认后才报告 `paid`。浏览器跳转、未经验证的回调和创建收银台成功均不是已支付证据。重复回调不得重复入账。
5. **异常处理**：异步支付未决或渠道查单失败时保持可核对状态；过期、取消与支付竞态不能把已收款订单误判失败。应支持按商户、外部引用和 TDCloud 单号对账，并给出退款、拒付后的状态/账务处理规则。
6. **授权与隔离**：商户服务端调用需要可撤销的凭据和最小权限；建单、查单、收银台跳转地址及结果不得跨商户泄露。需要定义限流、错误码和审计记录。

## 与支付插件的边界

插件保存 ZBoard 业务订单与 TDCloud 收款单的对应关系，调用 TDCloud 创建/查询收款单，并在 TDCloud 返回已确认支付后，把支付事实交给 ZBoard。ZBoard 自己完成业务订单、订阅和权益变更。两边各自维护订单状态；跨系统短暂不一致时，插件重试并提供人工对账依据。

TDCloud 已在独立仓库实现通用商户收款、`return_url` 和签名状态通知。插件的 `tdcloud/client.go` 已按[正式十进制金额契约](tdcloud-contract.md)对齐商户 OAuth、目录可用性、幂等建单和查单，新支付不依赖币种精度目录；`tdcloud/notification.go` 要求并验证签名请求头，随后仍由插件服务端查单。插件已注册公开 POST 路由，并在加密插件存储中维护 TDCloud 单号到支付尝试的索引。ZBoard 已完成插件注册路由请求透传。插件公开路由现可获取签名头，由插件定位已保存的支付尝试、使用其通知密钥验签并经 TDCloud 服务端查单；可信支付端口未绑定时返回可重试的 503，不把无签名请求体当成查单触发器。

## 验收条件

- 沙箱中用动态金额创建收款单，跳转支付，再由服务端查到包含一致金额、币种和稳定事件号的已支付结果。
- 同参数重试、不同参数冲突、商户越权、伪造/重复回调、异步支付和过期竞态均有自动化验证。
- 商户钱包只入账一次，账务和收款单可按外部引用对账。
- TDCloud 部署新接口、执行所需迁移与权限同步，并完成真实沙箱支付、退款和拒付验收；支付插件再做跨系统端到端验收。
