# ZBoard 插件管理操作的请求契约一致性

## 当前状态

已修复：ZBoard 提交 `abd968769a9f9054cca042fd5c52b8deff967a98` 的前端生命周期请求已移除 `version_id`，后端继续严格拒绝未知字段。2026-10-12 已在登录的线上插件详情页成功启用现有 v0.1.0，页面及操作记录均确认成功。下文保留原问题与验收边界，供回归检查。

## 问题与边界

2026-10-12 在支付插件管理页复现：点击“启用插件”并确认后，页面仅提示“插件操作失败，请刷新状态后重试”，操作记录没有新增“启用”。已安装包通过宿主准入，按钮可点击。

在 ZBoard 提交 `19f12184f7cb92b89ff85ca01454a2503caa47cb` 的隔离副本中，通过真实 HTTP handler 和插件进程确认原因：

- `frontend/src/api/plugins.ts` 的 `pluginAction` 总是发送 `generation`、`accept_untested`、`version_id`；启用时 `version_id` 为 `""`。
- `backend/internal/handler/plugins.go` 的 `AdminPluginActionHandler` 请求结构只接受 `generation`、`accept_untested`。
- `pluginBody` 使用严格 JSON 解码，拒绝 `version_id`，返回 HTTP 400 和 `invalid or oversized plugin request`。请求在进入插件管理状态机及插件进程前被拒绝，因此没有操作记录。
- 移除 `version_id` 的相同请求可成功启用插件。管理员配置会话的读取、保存、检测也已通过实际插件联合测试。

这是宿主通用插件管理页面与接口的契约冲突，影响所有通过相同入口执行管理操作的插件。修复不涉及支付渠道、订单或 TDCloud。

支付插件没有宿主管理接口的控制权，不应增加自行启用入口、绕过 JSON 校验、读取管理员登录凭据或直接调用宿主私有管理接口来补偿。

## 要求

1. 统一现有生命周期操作的前端请求与后端允许字段。当前操作列表为 `enable`、`disable`、`uninstall`、`purge_data`，前端不再发送后端不支持的 `version_id`。
2. 不为解决本问题恢复已移除的回滚协议，也不放宽所有管理请求的未知字段校验。
3. 管理操作失败时，界面展示宿主返回的可理解错误原因，避免所有失败都退化为“操作失败”。
4. 继续保留管理员鉴权、代次检查、兼容性、能力准入、迁移和程序启动校验。不能通过忽略错误或假报启用成功来修复。

## 验收条件

- 从真实插件详情页点击启用，通过浏览器发送的实际请求进入管理状态机，出现启用操作记录；成功后显示已启用，重载页面仍然已启用。
- 停用、卸载及清理数据使用与后端一致的请求字段；对应的既有确认、状态与数据保留规则不变。清理仅在隔离测试数据上验证。
- 代次过期、非管理员、不兼容、迁移异常和进程失败仍正确拒绝；界面显示对应错误。
- 添加前端请求形状与 HTTP handler 的联合回归测试，覆盖浏览器实际序列化的请求，而非仅直接调用 `Manager.Action`。
- 支付插件配置表单在停用状态下仍可打开，保存与检测通过已有 `config.load`、`config.save`、`config.test`，无需新增渠道特定宿主能力。
