# 需求说明：完成通用插件支付扩展能力开放

> 状态更新（2026-10-12）：ZBoard `3e0ca9b` 已发布对应通用支付契约。本文保留为需求与验收基线，附录是提出需求时的代码状态，不是当前缺口清单。当前适配依据为公开 SDK 的 `commerce.md`。

## 1. 需求目标

请在 ZBoard 现有插件体系中，开放订单支付扩展点、插槽后端动作调用、原生插件商务授权，以及结算上下文和受控开窗能力，使支付插件可以接入现有订单确认页和订单页。

ZBoard 继续持有业务订单，并使用现有商务事务完成订单、订阅和权益；支付插件负责支付方式、渠道接入和支付结果核实。本需求适用于所有支付插件，不包含任何支付渠道的接口、凭据、验签协议或状态转换实现。

## 2. 预期用户流程

1. 用户打开订单确认页。商品、规格和价格正常展示；支付方式区域异步加载已启用插件提供的选项。
2. 用户选择支付方式并点击支付。当前点击立即预留新窗口，原页显示简洁的等待/确认界面。
3. 原确认页通过现有业务流程创建订单，将订单标识交给所选插件。插件后端读取可信订单数据，创建渠道支付订单；新窗口导航到插件返回的收银台地址。
4. 用户完成支付后，点击原页“已支付，确认”，或从支付窗口返回 ZBoard 订单页，触发所属插件的服务端核对。
5. 插件核实支付结果后，通过受限的原生插件授权提交支付事实。ZBoard 在已有事务中完成订单及相关订阅、权益。
6. 原页确认、返回页核对和后台通知可能同时发生；这些入口共用同一事件身份，订单履约只执行一次。页面最终以 ZBoard 业务订单状态判断成功。

## 3. 职责边界

| 领域 | ZBoard 负责 | 支付插件负责 |
| --- | --- | --- |
| 商品和业务订单 | 商品/SKU、下单、续费、换套餐、抵扣、应付金额、订单归属及状态 | 引用宿主订单，不复制业务下单规则 |
| 插件运行与页面扩展 | 贡献注册/发现、会话、授权、生命周期、UI 挂载、资源限制 | 声明贡献、实现支付选项及等待/确认交互 |
| 实际支付渠道 | 不实现渠道适配 | 渠道配置、商户凭据、渠道订单、跳转、服务端查单和通知验签 |
| 支付事实 | 验证授权、订单归属、金额与币种，执行幂等商务事务 | 核对渠道结果与业务订单的关联，提交已核实的支付事实 |
| 订阅和权益 | 通过现有订单完成流程执行履约 | 不直接修改业务订单、订阅、权益或数据库 |
| 后台通知 | 按插件注册路由交付请求，执行通用准入和资源限制 | 解析通知、鉴权/验签、定位支付尝试、核对渠道结果 |
| 插件数据 | 提供现有隔离持久化能力 | 保存支付尝试、订单关联、渠道快照和重试状态 |

以下不在本需求范围内：

- 为特定渠道增加 ZBoard 核心代码或专用接口。
- 重建现有订单查询、支付事实、订阅或权益业务。
- 将浏览器返回、前端声明或未经核实的通知直接视为支付成功。
- 要求消费者创建、粘贴集成凭据，或向插件交付主站登录令牌。
- 让插件访问宿主数据库、内部 HTTP 或不受限的核心命令。
- 本期新增退款、拒付及逆向履约业务；这类业务若后续需要，另行形成通用需求。

## 4. 需要开放的通用能力

### R1. 订单支付 UI 扩展点

在现有订单确认页及订单页开放支付相关 UI 插槽（slot）：

- 确认页能够发现、加载已启用且获授权插件的支付方式贡献；支持多个插件贡献，不在宿主固定某个插件或渠道。
- 订单页能够恢复已有订单的支付操作，并在支付窗口返回时调用所属插件核对。
- 贡献声明、发现、授权和失效沿用现有插件机制；具体 slot 名称及上下文契约由 ZBoard 定义并公开。
- 商品和订单内容先正常展示，插件区域异步加载；局部失败可局部重试，不要求刷新整个页面。
- 不通过新增独立收银台菜单、借用其他用途 slot 来替代订单支付扩展点。

**当前缺口：** 已有通用 slot 机制，但允许清单没有订单支付位置，现有订单页面没有对应挂载点。商务订单读取权限还要求独立账户业务页，需要允许合法的订单支付贡献获得相应授权。

### R2. 授权 slot 调用所属插件后端

扩展现有页面动作分发机制，使合法 slot 会话可以调用其所属原生插件：

- 延续现有 `page.call` / `HandlePageAction` 或等效通用机制，不新增渠道专用 RPC。
- 宿主验证插件、贡献、用户、surface、会话及生命周期，再向插件传递可信 actor 和贡献上下文。
- 浏览器不能替换 actor、插件或贡献身份，不能借一个贡献调用另一个插件的后端。
- 禁用、卸载、权限撤销或会话失效后按通用规则拒绝动作。
- 明确 slot 标识如何传入原生 SDK；不要求插件把 slot 伪装成独立业务页面。

**当前缺口：** `SessionPageAction` 只接受独立业务页的 `purpose=business`，拒绝 `purpose=slot`。slot 会话有 `SlotID` / `Slot`，但没有 `PageID`，其动作上下文需要形成正式契约。

### R3. 原生插件的受限商务授权

向获授权的原生插件开放现有商务能力：

**读取订单：**

- 能取得授权范围内订单的 ID、稳定业务订单号、所属账号、最终实付金额、币种和状态。
- 金额采用宿主明确的最小货币单位及精度，使用业务订单的最终应付金额，不能由浏览器覆盖。
- 复用现有 `commerce.orders.list` 或其他公开订单查询；不强制新增单笔查单接口。
- 宿主校验插件身份和账号/订单权限；浏览器提供订单标识只是选择请求对象，不构成授权。

**提交支付事实：**

- 复用 `commerce.payments.record` 的业务语义、校验和事务，增加合适的原生插件授权路径。
- 写入权限只授予被批准的插件服务端，不直接开放给浏览器。
- 宿主验证订单归属、状态、应付金额和币种；插件负责核实外部交易的真实性及业务订单关联。
- 宿主决定稳定的支付事实身份及事件去重范围；普通进程重启、配置变更或升级不能改变同一支付事件的去重身份。
- 同一事件、同一内容的重试可安全重复；同一事件标识但内容变化必须冲突，不得再次履约。
- 对已完成订单重复提交或竞争提交，保持订单、订阅和权益只履约一次。

**后台调用：**

- 浏览器关闭或会话到期后，获授权的插件进程仍能核对其已有授权范围内的订单并提交事实。
- 插件保存的关联只用于定位订单，不自动成为授权；宿主仍需校验进程身份、授权范围和生命周期。
- 无浏览器会话的公开通知不能自行选择任意账号并取得商务权限。
- 禁用、卸载及授权撤销时遵循宿主通用规则；暂时不可用不得返回已成功入账的结果。

**当前缺口：** 已有账号范围订单查询，但原生插件 host service 尚未开放该调用；现有支付事实操作只接受 `integration` 身份。需要释放原生授权，不是复制已有商务实现。

### R4. 结算上下文和受控支付窗口

为支付 UI 提供宿主拥有的结算协作能力：

- 提供用于展示支付选项的结算币种、已有订单标识，以及当前订单确认流程所需的受控上下文。
- 复用原确认页的业务订单创建逻辑，将创建结果交给所选插件；插件不接管商品/SKU/续费/换套餐创建规则。
- 创建中的重复点击合并；恢复已有订单及未决创建，支付重试复用同一业务订单。
- 当前用户点击时同步预留窗口；建单完成后可导航，准备失败可关闭空白窗口。不能等异步网络请求结束才尝试开窗。
- 宿主可以提供通用窗口桥接，或为合法贡献提供受控弹窗权限；保留必要隔离，不强制整体放开 iframe 沙箱。
- 导航检查 HTTPS 地址及凭据等异常 URL；插件也应执行自身地址校验。
- 原页能展示简洁的等待/确认界面；iframe 方案需支持合适的尺寸或通用展示机制，避免确认界面被裁切。
- 提供或允许从受信任部署配置生成订单页回跳地址；不要求专门新增回跳地址 API。回跳仅用于导航和触发核对。

**当前缺口：** 现有桥接没有结算协作上下文及受控开窗端口；iframe 使用 `sandbox=allow-scripts`，无法直接打开支付窗口。

## 5. 已有能力及实现约束

- **插件注册路由请求透传已支持。** 本期不重复建设。保持原始请求体及验签所需的多值请求头等请求信息可交给所属插件；插件处理自己的业务，宿主保持路由准入及资源限制。
- **插件隔离持久化已支持。** 支付尝试、渠道快照及通知关联由插件自行保存，宿主无须新建渠道订单表。
- **订单查询和支付事实事务已存在。** 本期优先开放授权及调用路径，复用已有业务。
- 接口名称、权限声明、slot 名称及 SDK 形态由 ZBoard 按自身架构确定；本说明中的插件动作不是需要写入宿主的固定操作名。
- 必须提供明确的超时、大小、频率限制及错误语义，能区分未授权、会话失效、能力未开放、输入无效、事件冲突和暂时不可用。
- 插件进程存活与订单支付接线可用是不同状态。缺少商务授权时，不应误报支付成功；插件正常运行也不应被等同为商务能力已可用。

## 6. 验收条件

使用本地 ZBoard、签名测试插件和模拟支付服务即可完成开发验收，不以真实渠道付款作为前置条件。测试插件通过公开 SDK 接入；订单入账及订阅、权益使用真实 ZBoard 商务实现。

| 编号 | 验收场景 | 必须满足的结果 | 对应需求 |
| --- | --- | --- | --- |
| A1 | 安装并授权两个测试插件的支付贡献 | 确认页可发现并加载两者；禁用其中一个后其贡献失效，另一插件仍可用；没有独立收银台菜单 | R1 |
| A2 | 插件加载缓慢、超时或失败 | 商品、规格、价格仍正常显示；仅插件区域显示加载或失败，支持局部重试；不可用方式不能发起支付 | R1、R4 |
| A3 | slot 发起后端动作，随后伪造 actor、插件或贡献身份 | 合法动作到达所属进程并带可信 actor；伪造、跨插件和失效会话调用被拒绝 | R2 |
| A4 | 原生进程读取订单 | 返回授权范围内的最终金额、币种和状态；读取其他账号或越界订单被拒绝；无需消费者集成凭据 | R3 |
| A5 | 点击支付并重复点击，创建成功后重试支付 | 窗口先于异步建单预留；创建动作合并；重试复用同一业务订单；准备失败关闭空白窗口 | R4 |
| A6 | 未授权插件或浏览器直接提交支付事实 | 被拒绝；不产生支付事件、订单完成或订阅/权益变化 | R3 |
| A7 | 授权插件提交金额/币种不一致或越权的支付事实 | 被拒绝；业务状态与权益不变 | R3 |
| A8 | 模拟支付完成，原页、回跳页和后台通知并发核对，并重复投递同一事件 | ZBoard 支付事实幂等；订单、订阅和权益只履约一次；页面最终展示 ZBoard 订单完成状态 | R2、R3、R4 |
| A9 | 同一事件标识提交不同内容 | 返回冲突；不修改已记录事实，不再次履约 | R3 |
| A10 | 首次支付事实调用结果丢失或暂时不可用，重启后使用同一事件重试 | 可恢复核对；去重身份保持稳定，最终仍只履约一次 | R3 |
| A11 | 用户关闭浏览器或会话到期，再由测试通知触发插件核对 | 获授权进程可处理原授权范围内的订单；公开请求不能借此取得任意账号权限 | R3 |
| A12 | 缺少权限、撤销权限、禁用或卸载插件 | 动作/商务调用按生命周期规则失效；明确报告不可用，不发起无法完成的支付或误报入账成功 | R1、R2、R3 |
| A13 | 浏览器声明已支付、回跳带成功参数，或模拟服务仍返回未决结果 | 未核实结果不得产生支付事实；订单、订阅和权益保持原状态 | R3、R4 |
| A14 | 确认界面在 iframe 中显示及执行回跳 | 界面不被裁切，按钮状态清晰；可信回跳进入订单页并触发所属插件核对，回跳本身不更新支付状态 | R1、R4 |

验收证据应包括公开 SDK 调用结果、授权拒绝结果，以及并发/重试前后的订单、支付事件和订阅/权益状态。单纯进程健康、UI 展示或模拟插件返回成功，不能替代真实 ZBoard 商务事务验收。

## 7. 交付内容与协作方式

ZBoard 侧交付：

1. 上述通用扩展点及授权实现，明确各接口的输入、输出、身份来源、权限范围和生命周期。
2. 正式 slot 声明方式、SDK/桥接调用方式、稳定事件去重身份及兼容性说明。
3. 原生进程后台商务调用规则，以及结构化错误、超时和资源限制。
4. 满足上述验收条件的自动化测试或可重复执行的本地验证步骤。

支付插件侧在契约发布后，自行适配正式 SDK、声明支付贡献、接入结算上下文/窗口操作及原生商务授权，并与模拟支付服务完成联合验证。插件内部函数和渠道实现不作为宿主实现模板。
