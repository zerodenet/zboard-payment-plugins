# ZBoard 支付通道插件

[English](README.md)

ZBoard 持有商品、业务订单、订阅和权益；插件持有渠道配置、支付尝试、渠道建单、服务端核对及通知验签。插件通过公开原生 SDK 提交已核实的支付事实，ZBoard 使用已有事务完成履约。浏览器返回本身不证明已支付。

## 已接入的宿主契约

要求运行的 ZBoard 包含 `3e0ca9b` 引入的通用商务契约或后续兼容实现；不能仅凭版本号判断支持度，宿主仍须准入清单中的能力与贡献。

- 清单声明 `account.checkout.payment` 与 `account.orders.payment`，分别用于订单确认页、订单/支付返回页。
- 账户 UI 从 `checkout.context` 取得宿主选择的结算上下文，异步发现渠道并通过 `checkout.options` 发布方式，声明 `payments.prepare` / `payments.reconcile`。
- 选择方式、创建业务订单、同步预留新窗口、导航收银台、等待/确认控件及最终订单状态由宿主通用结算交互承接。插件 iframe 保持沙箱隔离，不自行开窗或创建业务订单。
- 原生动作读取 `PageActionRequest.Checkout()` 及宿主提供的订单范围身份；前端只提交方式 ID，不能提供账号、金额、币种或回跳地址作为支付依据。
- 进程启动已绑定公开 `HostClient.ListOrders`、`HostClient.RecordPayment`、可信回跳地址及 `HostStorage`。私有存储保留订单授权，浏览器关闭后签名通知仍可核对原订单。
- 确认、回跳和通知使用相同支付尝试及渠道事件；宿主确认支付事实入账后才标记本地已支付。重启和重试保留原渠道配置快照及幂等身份。
- 展示历史方式前先由宿主验证订单归属。已移除/停用的原方式可作为禁用选项保留，用于核对已有尝试，不用于新支付意图。
- 没有独立收银台菜单，也不要求消费者创建或粘贴集成凭据。

正式接口见相邻 ZBoard 的 `backend/pkg/pluginapi/v1/commerce.md`。[通用宿主需求基线](docs/zboard-plugin-payment-capability-requirement.md)保留为设计历史，所需契约已发布。

## 导入与渠道配置

在 ZBoard 导入签名离线包，授予声明的 UI/slot、配置、存储、注册路由、订单读取与支付事实写入权限，再配置并启用插件。运行的宿主须包含上述商务实现，并配置有效的 HTTPS 部署 `SiteURL`，供宿主生成可信订单回跳地址。

当前源码已注册管理员配置页 `settings`，停用状态下也能打开。入口统一为“添加支付渠道”，表单选择渠道类型后显示该类型的参数。目前已实现 TDCloud；已有密钥保留、移除确认和配置检测使用宿主已有配置桥接，仍可使用高级 JSON。

前端渠道适配器通过 `ui/channel-config-providers.mjs` 注册，TDCloud 字段独立在 `ui/tdcloud-config.mjs`。宿主当前禁止配置页声明业务菜单，并限制 `config.*` 仅供管理员配置会话使用，具体边界与验收见[通用配置页导航需求](docs/zboard-plugin-configuration-navigation-requirement.md)。插件生命周期管理与日常业务设置应呈现各自的导航位置。

配置编辑器接受：

```json
{
  "channels": [
    {
      "id": "tdcloud-main",
      "name": "TDCloud",
      "type": "tdcloud",
      "enabled": true,
      "settings": {
        "api_url": "https://tdcloud.example.com",
        "client_id": "merchant-oauth-client-id",
        "client_secret": "merchant-oauth-client-secret"
      }
    }
  ]
}
```

换成实际 TDCloud API 源地址及商户 OAuth 凭据。商户客户端需要 `merchant_payments.create` 和 `merchant_payments.read`。新订单不发送 `payment_no`，TDCloud 自己管理收银台支付方式及选择。配置测试验证 OAuth 和渠道目录，不创建支付订单；探测成功不等于订单已结算。

配置读取隐藏 `client_secret` 和 `notify_secret`。编辑时省略密钥会保留同一商户/地址的原值；轮换时填写新值。密钥和原生订单授权只留在后端，不进入支付方式数据。

### 统一收银台边界

TDCloud 本身是插件的一个支付选项。插件不要求管理员或消费者填写 TDCloud 内部支付渠道 ID，新建收款单不传 `payment_no`。TDCloud 收银台可在初始未选择支付方式时返回空渠道，之后在订单结果中返回内部选中的渠道。查单及通知依据商户授权下的 TDCloud 单号、外部订单引用、订单金额和币种核对，内部渠道 ID 的变化不构成外部订单冲突。

TDCloud 正式商户收款契约接受十进制金额字符串 `amount`。新建收款单直接提交 `"amount": "15.00"` 与宿主订单币种，不提交 `amount_minor` 或 `payment_no`。币种是否开放、精度和金额上限由 TDCloud 校验，内部支付方式由收银台选择。插件不查询或配置 TDCloud 币种精度；渠道目录仅用于验证商户访问和收银台可用性，不用内部渠道币种或登录要求限制外部订单。参见[适配器契约](docs/tdcloud-contract.md)。

配置检测验证商户 OAuth 和收银台目录，不创建收款单。配置页通过已有宿主桥接显示当前进程的最近检测结果；重启或配置变化后结果失效。配置加载不发起网络检测，诊断字段不作为商户设置保存。连接检测通过不代表已发生支付。

### 十进制金额与核对

ZBoard 已知的两位小数金额 `1500` 直接格式化为 `"15.00"`，使用整数运算，不转换为 TDCloud 最小单位。建单响应、查单与签名通知以十进制 `amount` 核对金额，允许等价尾随零（如 `"10.50"` 与 `"10.50000000"`），拒绝缺失金额、非法格式、不能精确表示为宿主金额的小数、溢出、金额或币种不匹配；不使用浮点数或四舍五入。当前协议不依赖结果中的 `amount_minor`、`currency_decimals`。签名通知仍须经过带授权的渠道查单，再提交支付事实。

新私有 `_amount` 快照仅固定协议版本 2 和订单币种；支付尝试已保存宿主金额、幂等键、回跳及通知参数。超时、重启、配置变化或渠道移除后，重试继续使用原值。TDCloud 明确返回 `invalid_amount`、`invalid_amount_precision`、`currency_unavailable` 时释放支付尝试供用户选择其他方式；不明确的失败及幂等冲突保留原尝试。

历史版本 1 或没有版本字段的快照保留原整数请求、渠道绑定与结果单位核对，避免改变原幂等参数。旧换算代码隔离在 `tdcloud/legacy_amount.go`，新支付不会使用；旧配置的 `currencies` 和 `payment_no` 会从当前配置移除，也不在商户表单展示。此前[币种元数据开放需求](docs/tdcloud-invoice-currency-capability-requirement.md)已由十进制契约替代。

### 可选建单参数

描述是可选字段，留空时省略，不用于补偿 Stripe 等内部渠道的参数要求。可选描述与回跳地址在发送和响应核对前去除首尾空白，业务订单引用、金额、币种和幂等身份仍严格核对。高级渠道配置可设置 `expires_in`：省略或 `null` 使用 TDCloud 默认的 1800 秒，也可设置 60～7200 的整数；零值无效。私有快照保存原有效期，重启或当前配置调整不改变未决订单；历史快照缺少该字段时保持原默认请求。HTTP 202 或收银台内的 403/422 不代表支付成功，也不能据此另建订单，应继续核对原 TDCloud 收款单。

### 回跳与通知

插件传递宿主提供的 HTTPS `return_url`，首次建单时固定该地址，同一幂等键重试继续使用。建单响应中的地址必须一致；回跳后仍需服务端查单与宿主订单状态核实。

启用“接收支付状态通知”后，填写 TDCloud 商户收款状态通知设置生成的签名密钥。该密钥与 OAuth Client Secret 不同，插件保存这份平台密钥用于验签，不再自行生成另一份。TDCloud 只在生成时显示一次，普通配置查询不会返回密钥，因此首次设置需要商户复制；同一商户的普通编辑留空保留原平台密钥。从旧单笔覆盖模式迁移时必须填写实际平台密钥，不能把旧插件密钥直接当成平台密钥。

通知域名默认带入当前已验证管理页的 HTTPS 源地址，可修改；注册路径 `/.well-known/zboard-payments/v1/tdcloud-notify` 只读。请将完整地址同步填写到 TDCloud 的默认通知设置。新表单保存 `notify_mode: "merchant_default"`，建单只发送 `notify_enabled: true`，不再传地址和密钥覆盖平台默认配置。插件中的地址是接收端引用，不会自动修改 TDCloud 设置。TDCloud 更换签名密钥后，新支付尝试需要使用同步更新后的平台密钥；已有尝试保留原密钥与请求模式。无模式字段的历史快照继续保留原单笔覆盖参数，避免改变幂等请求。

插件使用私有快照中的平台密钥验证签名，再通过 TDCloud 服务端查单提交支付事实。通知正文不能自行选择宿主身份。

未配置通知时，新订单显式发送 `notify_enabled: false`，确认和回跳仍可核对。配置变化不修改未决尝试的原通知参数。存储/商务调用暂时不可用时通知返回可重试响应。结算前核对到退款或拒付会进入复核；已结算订单的逆向履约不在本次范围。

## 加载及恢复

渠道并行发现最长等待 4 秒，完整结果按配置/币种缓存 60 秒；不缓存部分失败，也不隐藏其他健康渠道。入口有加载、空状态和局部重试，等待/确认控件使用宿主通用交互。

再次打开收银台前，插件检查渠道返回的有效期；已超时则先通过服务端查单。服务端确认付款窗口已过期后，沿用原 ZBoard 订单创建新支付尝试及幂等键；确认已付款则完成原订单。未决结果或查单失败保留原尝试，不再打开失效地址，并提示仍在核对原收款结果。本地时间超过有效期不能单独作为释放尝试的依据。

超时订单可点击“检查原收款状态”进行一次只读查询：先由宿主确认订单归属，再读取原尝试并通过服务端查单。此操作不建单、不改变尝试、不记录付款；保留渠道原始状态与归一化状态的区别，并对授权或查询失败给出固定公开说明，不展示凭据或收银台令牌。业务拒绝通过 ZBoard `pluginapi/v1/actions.md` 中的 `NewActionError` 公开契约返回；旧宿主安全降级为通用错误。

插件存储保存支付尝试、渠道单号索引及固定分桶的授权索引；使用宿主 CAS 修订号，并对短暂生命周期争用作有限重试。原尝试能在重启或当前渠道移除后恢复快照核对。

## 开发验证

公开 SDK 已通过 `go.mod` 和 `go.sum` 固定到 ZBoard 提交 `505d0b728ea6d3fd78730326718b2446bdef9a7b`，普通测试不依赖相邻仓库。打包和隔离宿主集成测试需要独立 ZBoard 检出目录：通过 `ZBOARD_DIR` 指定绝对路径，或默认使用 `../zboard`。CI 使用同一固定宿主提交。

```sh
go test ./...
go vet ./...
go test -race ./internal/runtime ./payment ./tdcloud
node --test ui/*.test.mjs
python3 scripts/check-host-integration.py
```

联合验证脚本创建 ZBoard 已提交 HEAD 的隔离副本，导入实际插件签名测试包，配置本地模拟 TDCloud HTTPS 服务，经过公开 SDK 验证不配置渠道精度时 USD、TDC、JPY 的十进制建单及结算，拒绝字段不匹配的查单与签名通知，并验证进程重启、确认/签名通知并发及真实宿主支付事件、订阅和凭据。模拟证书只加入临时测试二进制信任；不改原 ZBoard 仓库，不保留签名密钥，也不产生交付用离线包。

## 离线打包

检查通过后，构建包含 Linux/macOS、amd64/arm64 四个平台的包：

```sh
scripts/build-package.sh "$PWD/dist/zboard-payments-0.0.1.zbplugin"
```

使用 ZBoard 官方打包器校验签名及包内容；稳定的本地签名私钥保存在系统用户配置目录，位于仓库外。服务器导入优先使用与实际部署平台对应的包，减少传输体积：命令末尾加 `linux-amd64` 等平台名，只构建一个平台。Linux amd64 包约 5.4 MiB，四平台包约 21 MiB。也可沿用已有发布者密钥：

```sh
scripts/build-package.sh /absolute/output.zbplugin /absolute/private-key-file publisher-id all
```

后续更新保持签名身份稳定；更换签名密钥会使已保存的宿主订单授权失效。包内只有运行程序、UI、清单和公开签名，不包含商户凭据或签名私钥。

## 版本与宿主管理兼容性

首个正式版本为 **v0.0.1**，清单、运行程序和交付包统一使用 **0.0.1**。此前标为 0.1.0/0.1.1 的本地包仅为临时测试产物，并非发布版本，应使用纠正后的 0.0.1 包替换。

ZBoard 已在提交 `abd9687` 修复管理页生命周期请求，不再发送已移除的 `version_id` 字段；运行的宿主应包含该修复或兼容实现。管理员配置表单在停用时也能打开。[管理请求需求说明](docs/zboard-plugin-management-contract-requirement.md)保留为已解决的问题记录。

## 晚到账与收款核对

TDCloud 收款单过期后仍可能从 `expired` 变为 `paid`。过期表示支付窗口结束，不能永久排除已核实的真实付款。签名通知和服务端查单都按同一收款单、外部引用、金额及币种核对；有版本的旧状态不能覆盖新状态，已确认付款不会被晚到的过期通知抹掉。

新尝试保留所有旧尝试的完整私有渠道快照及单号索引。已核实的付款事实先持久化，再调用宿主记账；宿主响应丢失后，重启可沿用同一支付事件重试。多个尝试的不同付款分别保存：首笔被 ZBoard 接受的事实完成业务订单，多收款或关闭订单的晚到款进入管理员“付款核对”页面，按退款或人工处理流程处置。插件不自动退款、不开新业务订单、不重复开通权益。ZBoard 当前拒绝同一已结算业务订单的第二个不同交易号，该笔完整事实由插件保存并显式待核对。

`reconcile-payments` 使用 ZBoard 已公开的任务调度，每五分钟扫描最多 20 张订单，每张检查最多 10 个到期查单项；待支付项间隔五分钟，过期历史尝试按日继续对账。签名通知和用户主动确认不受该间隔限制。无浏览器无限轮询或进程私有循环，宿主须准入 `zboard.task.v1` 后才能执行自动补查。

插件版本仍为 `0.0.1`。私有数据格式 2 兼容读取旧格式 1，新增完整历史；宿主空迁移不改渠道配置，数据准备后禁止回退到旧格式读取器。旧版本只保留历史单号、已经丢失凭据快照的记录会显示“历史凭据缺失”，不能用当前配置猜测原授权，需由管理员在收款平台核对。

## GitHub Actions 与发布

`Checks` 在面向 `master` 的拉取请求和推送时运行：Go 竞态测试、vet、前端模块测试、发布校验、依赖锁定检查、隔离宿主集成验证和四平台开发包构建。开发产物使用每次运行临时生成的 `payments-ci-dev` 身份，保留 14 天，仅用于隔离测试。

`Release` 在推送 `v*` 标签或手动指定对应标签时运行，重新执行检查，确认源提交属于 `master`，然后在 `release` 环境完成四平台签名。发布前配置以下环境值：

- 密钥 `PLUGIN_SIGNING_KEY`：安全提供现有 base64 Ed25519 私钥，禁止提交到源码。
- 变量 `PLUGIN_PUBLISHER_ID`：保留现有发布者身份。
- 变量 `PLUGIN_PUBLIC_KEY`：对应的 base64 公钥。

流水线核对版本、标签和密钥身份，所有包验证通过后创建草稿并发布；已有发布产物禁止覆盖。Release 包含 Linux/macOS 的 amd64/arm64 安装包、`SHA256SUMS`、`publisher.pub` 和 `release-metadata.json`，记录完整源码提交、兼容要求、发布者和产物摘要。导入前独立确认发布者信任。包内不包含商户配置、宿主订单授权或签名私钥。发布 Release 不会更新正在运行的 ZBoard 插件。
